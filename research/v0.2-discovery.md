# v0.2 standard diesel discovery and offline OEM research

Development and verification on 12 October 2026 used software fixtures only. No serial vehicle connection, ECU identity query, session transition or OEM request was performed. Existing vehicle observations do not establish support for these additional PIDs.

## Standard evidence and edition boundary

Decoder metadata cites the [SAE J1979-DA OCT2011 edition](https://saemobilus.sae.org/standards/j1979da_201110-j1979-da-digital-annex-e-e-diagnostic-test-modes), its [consulted annex copy](https://www.e90post.com/forums/attachment.php?attachmentid=1509324&d=1476497126), and the [DashLogic reference](https://www.dashlogic.com/docs/technical/obdii_pids). The copyrighted annex is not distributed with this project. Formulas, field flags, units and expected lengths are implemented in `mokka_ecu_lab/sensors/diesel.py`; each Discovery detail/export includes that metadata. STANDARD_DOCUMENTED identifies published semantics, independently of vehicle verification, which remains UNVERIFIED.

Implemented requests: 0173 exhaust pressure; 0178/0179 exhaust temperatures; 017A/017B DPF pressures; 017C DPF temperatures; 017F cumulative run times; 0183 NOx; 0185 reagent system; 0186 particulate matter; 0188 SCR inducement; 018B diesel aftertreatment. Only advertised requests enter a user-started scan. Field support flags also gate individual measurements.

The 8B decoder distinguishes A support bits from B status/type bits. Its normalized trigger is not a universal soot/blockage percentage. Regeneration interval averages describe exponentially weighted historical successful active events, not distance since the latest event or a last-ten arithmetic mean. No regeneration notification, health threshold, blockage diagnosis or unsupported replacement measurement is generated. PID 86 uses the primary annex's mg/m³; the secondary reference's mg/mm³ differs and is not used. PID 85 tank level comes from F under A bit 2; warning time is stored in seconds.

PID 88 was corrected in v0.2.3 after inspecting OCT2011 B115 pages 82–84: the documented layout is exactly 13 data bytes. The earlier three-byte restriction was erroneous, not a verified older layout. Three-byte responses remain unverified raw evidence. Current A flags are separate from latched B/C history; D–M contain five unsigned distance counters. Reserved current bits and inactive reasons fail closed. Published decoding does not assert ECU implementation or physical accuracy.

## Discovery and reception

Normal connection retains the original ten-sensor workflow and stops bitmap initialization at 0140. Explicit **Scan standard PIDs for selected ECU** pauses basic polling and permits additional bitmap pages 0160 through 01E0 only when the immediately preceding page from that ECU advertises continuation. A missing advertised page leaves later support UNKNOWN; a closed chain yields UNSUPPORTED. Another ECU's bitmap never grants support to the selected ECU. Functional standard OBD requests can elicit responses from multiple ECUs; this is not physical addressing of one ECU.

Only the twelve code-owned standard PIDs are eligible. Completion disables advanced transmit scope and leaves timestamped samples. **Monitor available standard PIDs** is a separate explicit action after discovery; it shares the same scheduler/cap with basic sensors. Stop revokes that scope. Resume restarts basic polling. Reports distinguish AVAILABLE, UNSUPPORTED, UNKNOWN, UNVERIFIED, NO_SUPPORTED_FIELDS and INVALID / UNVERIFIED; availability means a decoded sample exists, not freshness or hardware accuracy. Original framing is retained in the transaction journal and advanced sample metadata. A later error preserves any last successful value as historical evidence with an error timestamp.

Reception follows documented [ELM327DSJ](https://www.elmelectronics.com/wp-content/uploads/2016/07/ELM327DS.pdf) CAN automatic formatting/flow control and the [STN reference manual](https://www.scantool.net/scantool/downloads/234/stn1100-frpm-preliminary.pdf). Discovery requires an identified ECU and ISO 15765-4 CAN protocol 6–9. Fixed ATCAF1, ATCFC1 and ATAL configure documented adapter reception; no custom header, manual flow-control frame or UDS session command is sent. The adapter generates ISO-TP flow control as needed. The 4 req/s ceiling counts application adapter/OBD commands, not all physical CAN frames generated by the interpreter.

The parser supports classic CAN 11/29-bit headers, compact 18DA 29-bit replies, optional DLC, single frames, first/consecutive frames, sequence wrap, exact declared lengths and final padding. State is per transaction and ECU. Malformed, orphan, duplicate or truncated streams cannot produce measurements; other complete ECU streams remain usable. Headerless ELM CAF1 length/numbered output can be decoded offline but has no ECU attribution; ambiguous mixed output is rejected. CAN FD, extended ISO-TP addressing and cross-transaction stream recovery are not implemented. Adapter firmware compatibility still needs physical confirmation.

## Bosch MD1CS003 candidates

The [Peugeot forum](https://www.forum-peugeot.com/Forum/threads/obd2-dpf.131744/) contains VLud's first-hand report dated 2 April 2023, post #19: D525 average distance over ten regenerations, D526 estimated soot, D52F estimated ash, D532 estimated deterioration. It also mentions 1003 and an addressing pair 6A8:688. These are reported candidates, not an Opel address map or verified units/formulas. Later unsuccessful attempts using other addresses reinforce the compatibility uncertainty.

The [arduino-psa-diag repository](https://github.com/ludwig-v/arduino-psa-diag) and its [ECU list](https://github.com/ludwig-v/arduino-psa-diag/blob/master/ECU_LIST.md) associate CMM_MD1CS003 with a reported injection addressing group shared by other ECU families. They do not establish this Mokka's actual ECU software/calibration, these four numeric layouts, or a compatibility matrix. Its diagnostic/coding/flashing mechanisms are not integrated; no third-party implementation code was copied.

All four 22 requests remain RESEARCH_ONLY / UNVERIFIED, live_enabled=false, without numeric decoders or transmit controls. Standard differential pressure, temperatures, NOx, reagent and regeneration-state candidates use the Mode 01 paths above. Distance since the last regeneration, absolute OEM soot/ash mass and OEM deterioration remain unknown rather than inferred from 8B averages.

Before any future OEM implementation, collect independently supplied ECU hardware/software/calibration identifiers, engine/emissions variant, documented DID definitions including byte count/scaling/units, proven addressing for that exact variant, and reference positive 62 replies with comparison measurements. Offline identification evidence may come from an existing authorized diagnostic-tool report; this app does not query VIN or UDS identity. Matching only the MD1CS003 family name is insufficient: firmware can change supported DIDs, semantics and session requirements.

A future controlled read-only test requires separate explicit user approval of the exact requests, ECU/address, operating conditions, timing, stop criteria and reviewed policy change. The present authorization excludes 1003, security access and session transitions. If a candidate requires such a transition, it cannot be tested under this delivery's policy. The consolidated standard validation below does not authorize OEM requests.

## One future consolidated stationary vehicle session

This session is deferred until after offline delivery; no separate v0.1.1 live repetition is required beforehand.

1. Park safely in a ventilated place, apply the parking brake and follow vehicle/adapter instructions. Close OBDwiz and all competing clients. Confirm the outgoing MX+ port, normally COM4, with its documented host baud. Keep original recordings. Start a new recording before **Bluetooth serial → Connect** with ignition/engine in the documented diagnostic state.
2. Verify retained ATI/STI, accepted adapter setup, protocol and per-ECU 0100/0120/0140. Check the original ten-sensor workflow, negative-response/stale handling and source selection during this same session. Never treat previous idle values as fixed acceptance constants. If there is no identified CAN ECU or errors require reconnect, stop and investigate; do not probe addresses.
3. Open Discovery, explicitly select the responding ECU and start one standard scan. Check each requested later bitmap against that ECU's preceding continuation bit; inspect all twelve candidate rows as AVAILABLE, UNSUPPORTED, UNKNOWN, UNVERIFIED or unsupported fields. Save **Export discovery report**. Inspect raw ISO-TP frames, support flags, payload lengths and source headers before accepting any number. Record all 13-byte PID 88 fields with documented current/history semantics; retain unknown lengths as raw evidence.
4. If clean replies permit monitoring, explicitly start standard monitoring for a short controlled idle session. Record aggregate request timing (≤4 application requests/s), per-field units and update times. Compare supported values to a trusted separate diagnostic-tool recording under equivalent controlled conditions after releasing the COM port; record timing/conditions and discrepancies. Regeneration status may remain inactive at idle; do not force regeneration, induce faults, drive to trigger a state or interpret pressure as blockage.
5. Use **Finish session**, then **Disconnect before switching ignition off**. Confirm no later requests, closed raw/SQLite session and released COM port. Export CSV plus original diagnostic JSONL for private inspection, replay offline and compare reconstructed fields/status/errors with the journal. Do not upload identifiable vehicle originals automatically. Add VEHICLE_VERIFIED only after adequate exact-ECU payload and independent semantic evidence, never merely because a numeric sample appeared. Stop/rejection/disconnect regressions can remain simulated when provoking them physically would be inappropriate.
