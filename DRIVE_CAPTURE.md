# v0.2.1 Drive Capture operator guide

This release prepares one consolidated stationary-discovery and short-journey recording. All implementation checks use simulation; actual vehicle support, accuracy, Bluetooth behavior and road reliability remain unverified. Existing standard/OEM request permissions and the aggregate 4 application requests/s ceiling are unchanged. D525/D526/D52F/D532 remain offline research only. No session transition, brute-force scan, regeneration command, write/reset/clear/coding/adaptation or automatic reconnect is introduced.

## Windows executable

The local package is `release/v0.2.1-windows11/MokkaECULab/MokkaECULab.exe`. Keep its `_internal` folder alongside it. Download the complete Windows ZIP from [release v0.2.1](https://github.com/angelosmiliotis/mokka-ecu-lab/releases/tag/v0.2.1), extract the folder and run that executable. Previous v0.2.0 folders and its [release](https://github.com/angelosmiliotis/mokka-ecu-lab/releases/tag/v0.2.0) remain available as a fallback.

## Exact button order

1. Park safely with the parking brake applied, follow vehicle/adapter instructions, and close OBDwiz/other clients. In Dashboard select **Bluetooth serial → outgoing COM4 (confirm on this computer) → 115200 → Connect**. Check separate adapter/ECU statuses and the responding ECU. Do not use incoming COM3 by default.
2. Press **Start Recording**. Starting recording before Connect is also supported when initialization evidence is desired. Leave recording on across discovery and monitoring; no additional recording session is opened at the transition.
3. While stationary, open **Discovery**, choose the ECU, then **Scan standard PIDs for selected ECU**. Wait for **Discovery ended**. Inspect all supported, unsupported, unknown and invalid rows. Missing/invalid fields remain unavailable. Stop and investigate significant communication errors; reconnect only explicitly after checking conditions.
4. Open **Drive Capture**, choose the same ECU, then press **Drive Capture** to prepare the preset. This sends **zero requests**. Review omitted choices/reasons, and optionally check/uncheck eligible standard PIDs. The preferred weights are 8B=4, 7A=3, 7C=2, 78=2, RPM=2, speed=2, coolant=1, MAF=1, reagent=1; other manual choices use weight 1. These are preferences, not promised supported sensors or update rates.
5. Optionally press **Journey Start**, then **Start Drive Capture**. The existing weighted scheduler continuously reads only the selected eligible PIDs; it does not repeat discovery. The original basic Dashboard/Resume workflow remains available. Checkbox edits are staged until Start Drive Capture is pressed again; applying an empty eligible selection stops monitoring. **Focused dashboard** shows at most seven readings, with unavailable values as a dash and historical values marked stale/recorded. Displayed intervals are observed, including pauses/discovery where those samples are in recent history, not guaranteed frequencies.
6. Make the short journey without driver interaction with the laptop. A passenger may add **Note** or journey markers; no interaction is required to keep capture running. Do not force regeneration, induce faults or interpret standard pressure/trigger values as universal blockage/health percentages.
7. After parking, optionally press **Journey End**, then **Finish session → Disconnect**, before switching ignition off. Finish session stops requests and finalizes recording. Queued local markers for the same recording are flushed even when Stop cancels a receive; they never send an ECU request. An in-flight cancellation record may be retained deliberately.
8. Press **Export Research Bundle** on Drive Capture for the just-finished session, or select a closed session in Sessions and use the same button there. Choose a local ZIP destination. Export is disabled while recording. Replay the redacted JSONL offline as needed; it never opens a transport.

## Selection and evidence rules

The preset and worker both require completed explicit discovery for the selected ECU and its own advertised bitmap support. Unsupported/unknown requests and advanced PIDs lacking valid supported fields are omitted with reasons. Manual choices cannot grant a new request permission. The worker revalidates selections at activation. Data stays associated with response identifiers; functional standard requests can elicit other independently supported ECU responses without inheriting their support.

Stop revokes advanced transmit scope; Resume returns to basic monitoring. Three consecutive ECU failures still stop acquisition and require explicit reconnect. Selecting a preset never starts or repeats discovery. Monitoring and discovery retain one original journal and decoded database. New advanced transactions retain previously observed support evidence so replay can decode a session whose recording began after initialization, without fabricating unrecorded bitmap transactions. Session evidence snapshots are stored durably in local SQLite metadata, with their own save timestamp; an export uses that session's snapshot rather than the current GUI or another connection.

The documented OCT2011 decoder limits remain: PID 88 accepts three data bytes only, longer revisions remain unverified; 8B historical averages do not supply distance since the latest regeneration. Source edition, units, formulas, individual field support and vehicle UNVERIFIED classification remain visible in Discovery and its report. No physical validation was performed for this patch.

## Research Bundle contents and privacy

The ZIP contains redacted raw JSONL, decoded CSV, Discovery report, session summary (start/end/duration, versions, transaction/sent-request counts, weights), supported/unsupported/unknown PID summary, ECU response identifiers, observed per-PID/per-field sample counts and intervals, communication/decoding errors, markers, a manifest and SHA256SUMS.txt. Checksums cover all other files including the manifest; the checksum file cannot hash itself. Unknown recording/decoder versions and absent discovery evidence are listed in the manifest instead of invented. Legacy recordings remain exportable with those limitations.

Original raw journals are unchanged. Adapter/port identity and ATI/STI identification responses use the existing default redaction; personal session metadata/VIN are excluded. Free-text Note contents are additionally redacted by default, with the omission declared. Journey event names/timestamps remain. Private original notes are available in the local journal or an explicitly selected **Diagnostic support export** of JSONL; review originals before sharing. ECU response identifiers, timestamps and measured operating data remain diagnostic evidence and are not a guarantee of anonymity. The app never uploads a bundle or transmits it to a cloud.

## Reproduction

Run `python -m pytest -q` in the project environment. `scripts/verify_capture.py --output-dir release/v0.2.1-validation-final` runs the native Windows simulator through recording, discovery, preset preparation, weighted monitoring, all three marker types, Finish/Disconnect and the actual GUI bundle action. It checks recording continuity, seven focused rows, original raw preservation and every file checksum. The portable result is `samples/v0.2.1-validation.json`. Packaging occurs only after software tests pass; no result is a physical vehicle validation claim.
